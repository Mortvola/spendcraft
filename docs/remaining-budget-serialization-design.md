## Protocol and classification

Owning transaction → authorize owning Budget → existing applications FOR UPDATE → fresh relevant state after waiting → all protected queries/writes on that transaction → commit/rollback. A transaction, an unrelated row lock or a late Budget lock does not provide this protocol. Caller-gated helpers inherit participation; they do not each need another lock. Existing SQL row/FK locks are not a substitute for joining this application protocol.

Classifications:

- **ACCEPTED GATED**: current source follows the established protocol, with prior verification.
- **JOIN**: a callable overlapping writer needs the Budget boundary if retained.
- **JOIN AFTER POLICY**: the concurrency need is real, but lock-only implementation would leave independent semantics unresolved.
- **NO FINANCIAL GATE REQUIRED**: no demonstrated financial composition/deletion-admission defect requiring this boundary; other concurrency guarantees are not implied.
- **OPTIONAL LIFECYCLE HARDENING**: gate could produce fresh scope/dependency/error decisions, but financial corruption is not established or a serial-state policy is missing.
- **DEFERRED**: historical effect/recovery authority is unresolved; do not label gated arithmetic correct.

## What overlapping reads mean — not every conflict needs a Budget lock

Lucid dirty-field saves update assigned/dirty attributes, not every hydrated column. A Category settings object loaded before posting does not inherently overwrite Category.balance if balance was never changed. The same applies to Institution name versus cursor, or duplicate marker versus categories. A shared row alone is not proof of a stale financial overwrite. However, unchanged explicit request fields can be omitted by stale dirty tracking, producing a nonserial combination of configuration; that is a distinct demonstrated problem below.

Current type2/3 submission posts supplied allocation rows; it does not read fundingAmount/recurrence/goal settings to recompute a request. The proposal endpoint is read-side. A concurrent settings change can make a previously opened form stale, but there is no approved server “post with latest rules” or frozen-preview contract. A gate alone would not refresh client input. Do not recompute funding from current settings merely because configuration writers join the gate. Their separate settings-persistence race does justify fresh serialized settings reloads.

Category type/group/settings can race existence or scope checks. Some reference problems survive a valid serial order: Category DELETE checks active nonzero nominal usage, not funding-rule references/system status/zero balance. Locking settings cannot establish a stronger no-dangling-rule/no-system-mutation contract absent those rules. No independent semantic restriction is approved here.

## Concrete source-derived schedules

### 1. Unlink versus sync: identity/cursor authority, not balance-column overlap

A sync acquires Budget and refreshes token/cursor/Accounts, starts the provider call. Pause after obtaining response data but before local financial application. B unlink ignores Budget, removes the remote item and clears local token/cursor/Account identity/link provider IDs, then commits. A resumes with its pre-unlink snapshots/provider response. Old provider ID matching can no longer find the cleared identity, so a previously present transaction can be treated as new; A can also save a next cursor after B cleared it. No whole-row stale save is necessary: duplicate matching/cursor authority is the conflict. Exact provider/account result depends on response shape and remote timing; duplicate amount is a feasible source schedule, not newly measured production incidence.

The shared gate makes these local operations serial. Sync first→commit then unlink clears final identities. Unlink first→sync waiter refreshes, sees null token and rejects before posting. HTTP/queue/command sync already refreshes after the gate. Newly participating unlink/identity commands must reload themselves, too. Do not reuse a token lookup's model or a pre-wait provider response as current authority.

The existing remote removeItem call occurs before local mutation/commit. Budget serialization prevents a participating sync from interleaving locally, but cannot restore a removed provider item if local work fails. That is an independent recovery design boundary, not a reason to claim local locks are ineffective or to build a new compensator here.

### 2. CheckUnassigned versus PATCH: command overwrites a committed edit

Command reads empty categories and link amount5. Before its save, a supported PATCH commits amount10, explicit Category20=10 and corresponding balances. Command then writes its stale Unassigned99=5 JSON. The committed movement/Category effect reflects the PATCH, but nominal JSON now reflects the command's old state. This is demonstrated with the ACTUAL command body and deterministic inert save barrier in remainingBudgetWriters.spec.js. No database scheduling is claimed by this test.

If the command joins Budget first, then reloads empty-state eligibility, supported target shape, link amount and scoped Unassigned on that same transaction, it either makes its edit first or sees the PATCH and skips. No pre-gate list of hydrated models may survive a wait.

Independent semantics: absence of Category saves is NOT automatically a bug. When the prior empty-split lifecycle already applied an implicit Unassigned effect, making it explicit must not apply that effect again. Other historical rows may lack that evidence. Locking cannot decide which normalization is economically safe. Current command also has no type/deleted/eligibility/multi-link guard and uses a hasOne relation; no new selector or balance-repair policy is silently approved. Decide whether to retire the command or support a separately specified narrowly admissible normalization before implementing it.

The command's getUnassignedCategory() omits client:trx; transaction binding is an independent concrete defect for a protected implementation. It uses Promise.all across Budgets and Transactions. Adding locks inside those parallel callbacks would not serialize callbacks sharing an owning transaction and could create multi-Budget lock-order problems. Proposed retained implementation: sequential independent owning transaction per Budget; acquire before candidate queries; sequential/revalidated targets. No Category arithmetic redesign is proposed.

### 3. Account / Institution cascade versus posting

Cascade reads nominal allocation/Category balance without Budget. A gated posting can commit while cascade is paused; cascade saves a stale subtraction or removes rows after the writer admitted them. A gate can prevent that race only when the cascade joins before its authoritative reads, and all surviving state operations use it.

But current cascade reverses allocations without proving their original applied effects. A known CURRENT pre-start transaction may have no Category effect yet cascade subtracts its nominal amount; deleted rows can be reversed again; ambiguous multi-link/opening shapes compound ownership. These are independent correctness problems. Existing coherent current fixtures cannot distinguish all historical production states. No blanket skip/replay/conditional reversal or cascade lock-only fix is approved.

Branches: current coherent eligible ordinary reversal is calculable in a controlled trace; arbitrary historical reversal is blocked; opening/Pool is specialized and malformed shapes unresolved; whole-graph cleanup is nonfinancial if no balance survives. Provider removal before local financial preflight adds a distinct external failure/recovery issue. Source-known current forward defects remain real; do not relabel all of them historical, nor claim gate-only correctness.

### 4. Last-user / Budget destruction

Current DELETE /user deletes its own User before querying other users. With two users, concurrent transactions can each delete self, each still see the other's uncommitted User row and both decide not to delete the Budget. Both then commit, leaving no users but a retained financial graph. This is a source-derived READ COMMITTED schedule, not an executed PostgreSQL test. The comment explicitly intends last-user Budget cleanup, so the admission decision has an established meaning.

Acquire owning Budget BEFORE any User deletion, then freshly reload user/membership and other users on the same transaction. The first request can leave the second user; the waiter then sees itself as last and executes the current whole-graph branch. The same gate serializes against existing financial writers: posting first→teardown sees committed rows; teardown first→waiter finds no Budget and must reject/roll back. Whole-Budget cleanup does not need historical financial reversal because balances disappear.

This does NOT certify cleanup completeness. Current manual traversal, dependent-row FK/retention cases and remote calls need separate characterization. A gate does not make missing cleanup correct or rollback external deletion. Preserve current financial deletion formulas; do not reuse single-Account cascade reversal to delete a whole Budget.

### 5. Group and Category lifecycle

Group DELETE checks direct Categories before deleting. Concurrent Category creation or moving a Category into that Group can invalidate the check. Current schema migrations define categories.group_id FK; the race can reject through FK rather than create an orphan, but that does not ensure fresh409/404 endpoint behavior. Inspect live constraints only in a future authorized test. Gate only the deleter while leaving creation/moves outside the protocol does not close the race.

For consistent execution of the existing direct-Category admission/error contract, the rollout set is Group DELETE plus Category CREATE and Category UPDATE's group-move/admission path; Category DELETE already participates. All scope/parent checks must be after the gate. Gating the entire Category UPDATE endpoint is a possible bounded implementation tradeoff, not a requirement to lock pure name/goal changes for financial balance safety. Group.parent_group_id is a plain integer in current migration and Group DELETE checks no child Groups. Whether child Groups block deletion/reparent is a separate product question; adding gates cannot fix a valid serial orphan hierarchy under current rules. Group CREATE/UPDATE parent checks need joint coverage if that product rule is established. No new hierarchy rule is invented here.

Additionally, Validators/category.ts explicitly requires Category names unique within Group and Group names unique within Budget/parent scope. Current create/update routes check those predicates on default connections before saving; inspected migrations do not add matching composite unique constraints. Two same-name creations can both pass validation before either saves, or a rename can race creation. These are established admission invariants, not a proposal that names should be unique. The Budget gate can protect them only if ALL corresponding create/update/move writers participate and recheck uniqueness on the owning transaction after waiting. Include Group CREATE/UPDATE and Category CREATE/UPDATE, with Group DELETE/Category DELETE to close scope-lifetime races. Preserve current name scope and validation errors. Earlier ungated validator results must not authorize the post-wait write. Current Category DELETE already joins. A blanket no-metadata-gate rule would miss these predicate races; no balance column overwrite is required.

### 6. Existing-Institution Account creation

Creates a new Account and optional initial balance-tracked Statement. The Pool read is response-only; no opening or Pool save exists for transaction tracking. No competing writer can have already loaded the uncommitted new Account for normal posting. Thus no demonstrated shared balance lost update requires this route to join Budget merely for symmetry. Concurrent parent destruction may cause FK rejection/late validation; fixing parent lifetime and error semantics is separate from changing opening/Pool behavior.

### 7. Tax forecast first-save admission

TaxesController.post uses Tax.updateOrCreate({year,budgetId},{data:forecast}); GET selects the first matching Tax row. Installed Lucid wraps updateOrCreate in a transaction and SELECT FOR UPDATE, so existing-row updates are already serialized. However, if both requests find no matching row, there is no existing row to lock; each creates a row. Current taxes migrations add budget_id and NOT NULL but no Budget/year unique constraint. A and B can therefore both commit a first forecast, after which GET.first has two candidates and no ordering. This is a source-derived duplicate-creation race; no live duplicate incidence or PostgreSQL schedule was measured.

A narrow correction must acquire existing Budget, then use a plain scoped lookup and create/merge/save through the SAME owning transaction; the locking updateOrCreate helper is not permitted by the subsequent mandatory architecture. Both existence queries then run serially, so B finds A's committed row rather than creating another. Validation can stay before gate; actuals remain a read-side response. Avoid taking the Tax row lock first then Budget, and avoid calling upsert on its default client after acquiring Budget elsewhere. Existing duplicates, if any, require separate characterization; do not deduplicate or choose historical authority automatically. A new schema uniqueness constraint would also address first insertion but is not required to analyze the bounded gate option and is not proposed in this task. No tax calculation/inclusion/forecast policy needs changing to prevent two initial rows for the same upsert key.

### 8. Explicit Category settings can synthesize a nonserial state

Initial name Original, fundingAmount5. A explicitly submits name Original and fundingAmount8. B explicitly submits name B and fundingAmount5. Both load the original Category. Lucid dirty tracking makes A write only fundingAmount8 and B write only nameB. Both can succeed with final nameB/fundingAmount8, submitted by neither request and impossible under either complete serial application of those two provided field sets. This is distinct from legitimate partial PATCHes to disjoint fields. The actual updateCategory body is exercised with a scalar dirty adapter matching the installed Lucid comparison; the test demonstrates the schedule without DB execution.

FundingPlanController.updateOrCreateCategory writes overlapping funding fields after an ungated lookup, so it belongs to the same rollout set. Category UPDATE should gate before fresh Category/group/reference queries, then apply provided fields under current optionality. Funding-plan PUT should use the same gate and fresh Category. Do not change optional PATCH fields into a complete replacement API or add versions. No balance arithmetic or stale-form funding policy changes are needed. Pure names in unrelated single-field endpoints are not a reason for blanket locking; this case concerns interacting explicitly supplied settings fields and future financial configuration.

## Lock order, external work and same-transaction branches

New protected paths should resolve only immutable IDs/authorization before gate; acquire Budget before Institution/Account/Transaction/Category writes or User deletion. Never clear credentials or save a repair row first and acquire Budget afterward. Different Budgets must remain independent. Avoid multi-Budget transactions in retained operational normalization; if unavoidable, stable lock order must be explicitly specified, not Promise.all.

Current syncAll/provider financial branches are sequential. New-Institution batch shares one post-gate Pool object and one final save; accepted tests already cover its deterministic accumulation. Do not redesign it from Promise.all syntax alone. Existing user teardown parallel callbacks mostly remove distinct rows rather than computing shared balance deltas; a Budget lock still would not serialize these siblings. Error/rollback completion must continue awaiting all work; inspect failure paths rather than assume a lock supplies it. No broad parallelism refactor is approved here.

Existing online setup acquires a Plaid cleanup recovery-row lock BEFORE Budget. That is NEW source detail relative to overly general “Budget always first” wording: it is the accepted separate recovery lifecycle, not a lower financial row write. No observed reverse-edge deadlock is established. This existing protocol conflicts with the subsequent mandatory Budget-only architecture. Do not preserve or depend on its extra locks in a new correction; do not add a reverse edge. Recovery requires a separately scoped Budget-only ownership/lifecycle solution or an architectural blocker report. Existing cleanup attempt checks Institution without taking Budget, so adding it mechanically would materially alter the graph. Do not retrofit or extend a second lock hierarchy. See budget-serialization-architecture.md for the exact current non-Budget sites and the hidden Tax upsert lock.

Unlink's current network call can be inside Budget to serialize with sync's network/cursor lifecycle; long-held lock is an explicit tradeoff. Moving remote removal outside while retaining correctness requires token/generation revalidation and a recovery design, not a speculative optimization. Token/name input parsing and operator selection may occur before gate, but reauthorization/reload afterward is mandatory. Whole-Budget remote removals similarly are not transactionally atomic with PostgreSQL.
