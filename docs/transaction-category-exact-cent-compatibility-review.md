## Approved type-4 audit amendment

Type4 opening Transactions now follow the same signed account-linked conservation rule as types0/5: sum each individually rounded allocation in checked integer cents and compare against the single scoped AccountTransaction amount. Include every allocation, including Funding Pool entries; do not apply type2's opposite-sign rule. Pending/deleted/pre-start status does not exclude nominal conservation. Empty allocations sum to zero; missing or multiple links remain unsupported. The audit reports opening candidates separately as `opening` and in `byType["4"]`.

This supersedes earlier statements below excluding type4 from conservation. The older artifact's eight unsupported type4 outcomes were superseded by the accepted updated audit: all8 now pass. ## Inventory notation and count

R/W = reads/writes top-level Transaction allocation amounts; N = numeric runtime/DTO contract; A = arithmetic; C = value comparison/admission; API = serializes or consumes these allocations over HTTP. W is storage responsibility even when a caller supplies new numbers and therefore does not read stored strings.

There are **13 direct number-assumption sites requiring compatibility attention**: **10 demonstrated JavaScript hazards and 3 raw JSON-path numeric comparisons**. IDs H01–H13 below define the count, rather than counting every delegating route as another arithmetic defect. The three SQL comparison semantics must be verified in future PostgreSQL acceptance. Other paths are copy/contract boundaries, currently coercive operations, or SQL decimal readers; these still require regression coverage and are not falsely counted as broken addition. This is not a claim of 13 existing correctness defects with current numeric data.
