## 2. Funding Pool identity and special lifecycle

Pool is a Category row initialized at balance0 in the Budget's System Group, with type CategoryType.FundingPool. Budget.getFundingPoolCategory(options) scopes by type plus owning Group.budgetId. It is not a separate SQL balance table. Absence/duplicate/system-mode contracts are not invented here.

| Pool writer family | Special treatment / possible overlap |
| --- | --- |
| Opening/helper | Writes type4 date/link/JSON from Account.balance minus active, nonpending, on/after signed AccountTransaction sum; old opening amount determines Pool delta. Reads/writes require Account.$trx; caller must supply fresh Pool and save it once |
| startDate | Account current balance unchanged; ordinary Category crossings separate from opening. Pool fetched AFTER crossing writes, avoiding a stale pre-crossing Pool object |
| OFX | Transaction effects first, then fresh Pool/opening; LEDGERBAL/plaidBalance never arithmetic authority. Consistent replay commonly has zero Pool delta, but a missing opening can be created |
| Plaid first sync | Explicit initial provider Account balance, then applicable signed sum/opening; fresh Pool per sequential Account. Normal initialized sync does not continually recompute opening |
| New offline Institution | Adds opening for each Transactions Account; one shared Pool and one final save. Entirely Balances batch has no balance mutation; final unchanged Pool.save is not an absolute balance overwrite (ORM dirty fields) |
| Type2 funding | Pool normally a funder negative allocation; same grouped Category helper applies all economic rows. Base/config/transfer snapshots are not additional Pool writers |
| Type3 rebalance / ordinary postings | Can affect Pool when a valid scoped allocation names it; current server Category authorization does not exclude system types. Otherwise no Pool intersection. Do not infer UI presentation as an API restriction |
| Account/Institution cascade | Reverses stored opening Pool allocation and any nominal Pool split through generic Category subtraction, without independent opening authority/preflight |
| Repair | Administrative recomputation only, not approved historical reconstruction in this task |

Existing-Institution offline Account creation and addOnlineAccounts selection merely read Pool; balance-tracked initialization creates a Statement, not opening. Neither is another existing-Pool delta writer. Funding Pool special arithmetic must not be replaced with generic current Account eligibility; type2/type3 remain accountless.

## 3. Offline lost-update schedules and minimum change

Concrete current schedule: IC.addOffline hydrates Pool100; CC.transfer acquires Budget and commits type2 withdrawal20 → Pool80; initializer creates Account/opening+10 and saves its old Pool object as110. Correct composition would be90. Reversing ordering can instead let a posting writer overwrite initialization if it had already hydrated Pool before the ungated initializer committed. No PostgreSQL race was executed here.

Other actual intersections: two new offline Institutions each read100 and add10/20 can finish110 or120 instead of130. A startDate move can change opening80→100, adding20 to Pool; an initializer holding100 later saves110, losing that20 (expected130). Plaid first initialization adding30 or first OFX opening creation can similarly be overwritten. Ordinary CREATE/PATCH/DELETE or rebalance can intersect when they allocate Pool; otherwise their ordinary Category changes do not intersect this initializer. Online Account selection alone cannot lose a Pool effect because it does not write Pool.

Smallest repository change is addOffline's existing Budget query acquiring FOR UPDATE BEFORE its existing Pool fetch. Bind user/Budget/Pool/new graph to the same owning trx. Current validation can remain before transaction; create Institution/Accounts after the gate at their current relative positions. Only Pool financial authority strictly requires waiting, but moving no creation ahead of it avoids late lower-resource locks and simplifies rollback. No new global coordinator or opening formula is necessary. Applying the gate to the handler uniformly also covers mixed batches; all-Balances-only calls acquire a harmless extra gate rather than requiring a new tracking-mode branch. Existing-Institution addOfflineAccount need not join for this invariant; do not uncomment its opening call or make routes symmetric.

Promise.all is NOT an independently demonstrated balance race here: every new Account receives the SAME Pool instance, each += executes synchronously after awaited helper queries, the helper does not save Pool, and the outer handler awaits all branches before one final save. New Accounts cannot share an existing opening. Inert actual-handler characterization accumulates10+20−5 into125 with one save and three identical Pool references. Completion order may retain ordinary floating precision/order characteristics; do not redesign arithmetic or remove parallelism solely on suspicion. Provider shared separate-hydration branches were already serialized in accepted work. User graph cleanup parallelism destroys rows without shared balance RMW; Statement Promise.all changes membership, not Category balances.

## 4. Category deletion: actual contract and TOCTOU

Current established serial restriction: reject409/HAS_CHILDREN if ANY active (`deleted=false`) Transaction JSON row contains this Category ID with amount !=0. Test categories/deletionLifecycle covers committed success204, blocked409, transaction completion and rollback on late deletion failure. Group/Category ownership is scoped to actor Budget and requested Group.

The query has no pending, Account.startDate, Transaction-type or explicit Budget predicate: logical Category IDs are global and the Category itself is scoped. Consequently active nominal usage blocks even if the financial effect is pending/ineligible; deleted and zero-amount rows do not block. The endpoint does NOT check zero Category balance, system type, hidden state or funding-rule references. A Loan Category gets its associated Loan deleted through the same transaction. Do not add/remove these admission conditions as a concurrency change; missing system/zero/configuration policy is separate from TOCTOU.

Current sequence: transaction → Group/Category reads with client:trx → default db.query membership SELECT → optional Loan lookup/delete → Category DELETE → commit. No Budget gate. Source-approved race: deletion observes no usage; gated CREATE commits Transaction JSON+Category10; deletion proceeds from its earlier result and deletes Category. JSON has no FK to categories.id, and the old transaction_categories.category_id definition is a plain integer, not a constraint protecting JSON. A normal DELETE row lock can wait for an UPDATE but does not rerun the earlier SELECT. Result can be a committed Transaction allocation referring to a missing Category; a schema-specific Loan/other FK could instead fail/rollback, but does not supply the missing JSON admission protocol. No new PostgreSQL result is claimed.

Proposed: begin → bind/authorize Budget → Budget FOR UPDATE → fresh scoped Group/Category → membership SELECT **on trx** → fresh Loan dependency if applicable → normal deletion/commit. Reload after waiting: Category existence/group/type; active Transaction state and JSON allocations/amounts; the Loan row the current branch actually deletes. Do not reuse a pre-gate admission Boolean/model. No zero-balance/funding-configuration guard is added. Ungated metadata/type/group updates can still overlap those nonfinancial attributes; this bounded design certifies financial-posting membership order, not universal configuration/lifetime serialization. Any extension to that separate admission contract requires source-specific characterization, rather than silently gating every metadata endpoint. Preserve404 ownership/missing-resource behavior,409 membership behavior,204 success and rollback completion. A new scoped Budget lookup may precede existing Group404, but must reveal no foreign resource information.

Serial outcomes: CREATE/funding/rebalance or PATCH adding usage first → deletion409; deletion first → waiter's scoped Category authorization fails404 and all its financial work rolls back. PATCH removing final usage first → deletion204; while old nonzero usage remains, deletion409 is valid. PATCH amount changing nonzero to nonzero remains blocking; zero can become nonzero so requires serialization. Metadata-only edits introduce no Category balance effect. Providers already find/authorize Category rows inside their gate; missing auto-assignment Categories fail instead of authorizing an orphan. Preserve that existing error convention.

Ordinary startDate crossing does not rewrite nominal JSON, so a regular active nonzero allocation already prevents deletion before/after the crossing; pending is included in membership. There is no new ordinary membership to race into existence in that case. Legacy empty-split fallback/system Unassigned is a distinct special case, not proof that membership plus a gate certifies every system-Category deletion. Similarly Transaction DELETE normally only removes membership. Same-Category DELETE/DELETE may currently both report204 after independent reads; the proposed gate/reload gives204 then404. Different Categories in one Budget intentionally serialize; different Budgets do not.

## 5. Cascades: concurrency is not reversal authority

IC.deleteAccount resolves Budget outside its financial transaction, then binds it, loads Institution/Account, and calls the common deleteAccounts helper without a gate. IC.delete resolves Budget before trx, loads Institution/Accounts, and for connected Institutions calls remote removeItem BEFORE the common local cascade. Both share one sequential helper; there is not a second independent financial loop. Remote removal cannot be rolled back by local SQL failure; this recovery/product problem remains separate.

For each Account the helper queries links, finds owning Transaction, reverses nominal allocations (or Unassigned for empty JSON and Transactions tracking), deletes link/Transaction, cleans permitted BalanceHistory dependents and deletes Account. It does not filter deleted/pending/date/type before subtraction. Budget/Categories survive Account/Institution deletion; their financial effects therefore matter even though the Account balance disappears.

| Current branch | Primary cascade classification | Reason / surviving state |
| --- | --- | --- |
| Ordinary explicit JSON allocations (including deleted or pre-start rows) | **HISTORICALLY AMBIGUOUS REVERSAL** | Canonical stored rows do not establish old Category application. Same nominal shape can mean currently ineligible zero effect or old applied effect |
| Empty JSON, Transactions tracking → subtract link amount from Unassigned | **HISTORICALLY AMBIGUOUS REVERSAL** | No stored applied-effect evidence; pending/deleted/date ignored |
| Opening/type4 → Pool nominal subtraction | **UNRESOLVED SPECIAL LIFECYCLE** | Normal new initializer fixtures prove a particular effect; arbitrary old/multiple/deleted/malformed opening state is not certified by its nominal row |
| Loan Account / multi-link or shared Transaction | **UNRESOLVED SPECIAL LIFECYCLE** | Generic loop can delete a Transaction still referenced by another Account; principal/interest/ownership/lifetime semantics are not resolved |
| Empty JSON, Balances tracking | **NONFINANCIAL ROW CLEANUP** for surviving Categories | No Category subtraction branch; Account/Statement/link/FK cleanup can still need its separate contract |
| Missing Transaction / row cleanup, histories / Account/Institution rows | **NONFINANCIAL ROW CLEANUP** | No inferred balance reversal needed merely to remove rows. Existing FK/orphan behavior is not redesigned |
| Normal type2/type3 accountless records | No cascade branch: **IMPOSSIBLE** under valid lifecycle | Zero Account links; do not manufacture an Account-cascade reversal |
| Whole last-user Budget graph | **NONFINANCIAL ROW CLEANUP** | Categories/Pool also disappear; no surviving balance to reverse |

No generic stored-state branch independently establishes SAFE FINANCIAL REVERSAL for every historical Account. A deliberately controlled new Account/opening history can prove its own applied effect for a characterization fixture, but that is not an admission marker for arbitrary production records. Do not introduce one here.

Independent concurrency example, assuming a separately proven old effect10: cascade hydrates Category100; funding commits−20 →80; cascade saves its old100−10=90, losing20 (correct70). Two cascades can similarly overwrite a shared Category; an Account posting after a cascade enumerates links adds a lifetime race. Adding a gate could serialize these reads but would not prove the subtraction10 correct, prevent old offsets, or resolve multi-link/provider recovery semantics. Defer broad cascade migration; do not advertise bounded work as universal Category correctness. Operations involving an ambiguous cascade remain blocked by semantics even where a lost-update schedule is identifiable.

## 7. Options, locking, binding and rollout

**Bounded Budget extension (recommended).** Reuse the existing query/pattern, no coordinator or lower-resource hierarchy. Required additions: IC.addOffline and CC.deleteCategory only. Retain/reverify existing manual CREATE/PATCH/DELETE, startDate, both OFX entries, Plaid sync and funding/rebalance gates. Existing-Institution addOfflineAccount, Statement-only initialization, Category metadata-only saves, new zero Categories/Loan rows, whole-graph cleanup and unrelated reports need no new balance gate for this bounded invariant. Cascades explicitly remain deferred, so no claim covers arbitrary overlap with them.

Offline Pool is already explicitly queried on trx; retain user→Budget→Institution→Account relationship transaction propagation, sum/opening/link saves and final Pool.save. Category DELETE's default membership query must acquire/use the SAME trx as Budget/Category/Loan deletion. Budget.getFundingPoolCategory/getUnassignedCategory use supplied options, not automatically this.$trx: pass client explicitly for protected mutations. The existing-Institution response-only getUnassignedCategory() default connection is outside protected financial work; do not call it a lost-update writer. Cascade Category.find reads use budget.$trx but are global IDs from stored JSON; transaction binding does not prove ownership/history. Budget pre-lookups outside trx must not be reused for mutable financial state if cascade work is later approved.

No new same-transaction parallel Category/Pool mutation defect was demonstrated beyond already-corrected provider branches; shared-instance offline accumulation is proven separately from cross-request stale persistence. Do not broadly remove Promise.all. Existing atomic JS += does not make the eventual SQL save atomic against another transaction.

**Category-row locks:** a DELETE row lock cannot force a posting writer to rerun its already-made Category admission or make JSON acquire an FK. Consistent early Category locks by every writer could work but require discovering/sorting multi-Category sets and changing existing acquisition order. Adding only FOR UPDATE to DELETE after its membership check is insufficient. Do not introduce that architecture for this task.

**Atomic SQL deltas:** can compose pure concurrent increments without stale balance assignment, but do not serialize existence/membership decisions or guarantee the Category still exists. Opening still depends on fresh Account/link/opening state and caller ordering; mixed deletion/repair/absolute writes remain. A zero-row UPDATE needs a lifecycle error, not silently dropped effects. Precision policy is separate. Not a universal fix and broader than reusing the existing gate.

**Optimistic version/check/retry:** no common Category version protocol currently protects all writers. Schema or original-balance comparison plus transaction-wide retry would need multi-resource rollback, deletion handling, logs and provider cursor semantics. It does not infer historical authority; not recommended for the bounded extension.

**Deadlock ordering:** both recommended paths should acquire Budget before any mutable Category/Pool/Account/opening row lock. Do not create an Institution/Account first and then wait for Budget. Current addOffline lacks a late gate; adding it at the existing Budget read makes all creation later. Current Category DELETE has ordinary lower-row locks only when deleting (after its check); put the new gate before all those reads/deletes. Existing accepted financial writers already gate before lower financial writes; no conflicting lower financial lock-before-Budget was found in that set. Provider setup's cleanup/recovery-row lock can precede Budget, but the proposed paths never acquire that recovery row, so they introduce no reverse edge. No new Account/Category prelock hierarchy is needed.

Wait-for consequence: same-Budget participants wait on one Budget owner before acquiring lower financial locks, so participant cycles through shared Categories are avoided; they cannot hold a Category while waiting for that owner's Budget. Ungated cascades, configuration/graph lifetime operations and administrative multi-Budget repairs are outside that guarantee. A conditional existing outsider cycle is also source-feasible: manual CREATE holds its Account row after Account.save and waits on a Category; an ungated cascade holds that Category after subtraction and later waits to delete the same Account. Wait-for graph: CREATE → cascade (Category), cascade → CREATE (Account). This is a risk schedule, not an executed PostgreSQL deadlock or a reason to invent lower prelocks. It reinforces the explicitly bounded guarantee and deferred cascade lifetime/authority work.

Different Budgets have disjoint scoped Category/Pool sets under valid supported shapes and remain independent. Corrupt historical cross-Budget Category IDs in the cascade's global lookup are not legitimate multi-Budget operations or newly certified safe targets. CheckBalances can lock multiple Budgets without an explicit stable ordering; operational deadlock/long interactive hold remains separate and the command must not be run here.

**Lock duration:** auth, request parsing/immutable validation and nonfinancial preparation can precede gate. Authoritative Pool, Category membership/dependency and Account/opening reads must follow it. Offline creation and Category deletion have no necessary external network call. Plaid's existing gate across pagination/network is an accepted contention tradeoff, not redesigned. Do not move Institution remote removal into the bounded design.

**Deployment boundary:** ship the two additions and Category membership binding together as one bounded correction, preserving existing gates. No need to migrate all monetary writers or change schemas. A partial deployment can protect one of the two identified defects but must not claim both fixed. Mark cascade overlap explicitly unsupported by the bounded guarantee until separate authority/lifetime/recovery policy is resolved. No new API errors, retry protocol or monetary representation is required. Preserve tenant scope/404 behavior, and do not let acquisition of a Budget authorize a foreign Group/Category.
